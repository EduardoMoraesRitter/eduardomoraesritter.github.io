> Objetivo: extrair a ESTRUTURA que fez o Wave-Racer funcionar e usá-la como
> molde para criar um jogo novo.

---

## 1. Por que o prompt funcionou (a tese)

O prompt não é um pedido de jogo — é um **sistema de produção** embutido em
texto. Ele define quatro coisas que prompts comuns não definem:

1. **O produto** em mecânicas verificáveis (não "um jogo legal", mas "4 barcos,
   3 voltas, flutuação em 5-6 pontos do casco").
2. **A régua de qualidade** com condição de fracasso explícita ("se alguma
   superfície parecer PBR, você falhou na direção de arte").
3. **O método de trabalho** (subagentes, harness de verificação, crítico
   severo, loop até secar, milestones jogáveis).
4. **O critério de parada** ("o crítico não consegue mais nomear nenhum
   defeito específico" — não uma nota, não um "ficou bom").

A frase-resumo: **substituir "confie na IA" por verificação externa em loop.**

Validação nossa: reaplicamos o método no clone e ele funcionou duas vezes —
rodadas visuais (HUD 29%→8,9% da tela) e pipeline de áudio (harness com 38
checks + juiz Gemini + ouvido humano como régua final).

## 2. Anatomia do prompt — os 7 blocos

| # | Bloco | O que faz | Frase-chave do original |
|---|-------|-----------|-------------------------|
| 1 | **Ambição + anti-escopo** | Calibra o alvo; proíbe entregar protótipo | "Not a demo, not a prototype — a finished, beautiful, playable game" |
| 2 | **Restrições inegociáveis** | Stack fechada, zero assets, performance como requisito | "If it isn't generated by your own code, it doesn't ship" |
| 3 | **Direção de arte com condição de fracasso** | 1 estilo, referências reais, técnicas nomeadas | "If any surface reads as physically based, you have failed" |
| 4 | **Subsistema-estrela** | O elemento que carrega o jogo ganha seção, agente e iterações extras | "The water — treat this as its own AAA-sized problem" |
| 5 | **Mecânicas verificáveis** | Números e comportamentos checáveis a olho | "Buoyancy sampled at 5–6 hull points" |
| 6 | **Método de trabalho** | Subagentes, harness ANTES de tudo, crítico, loop, milestones, honestidade | "Every visual claim gets verified against a real captured frame" |
| 7 | **Entrega + gatilho** | Repo, README, comandos funcionais + `Ultracode.` | "npm install && npm run dev" |

### Por que cada escolha é esperta

- **Stack fechada** → elimina decisões de infraestrutura (onde IA perde tempo).
- **Zero assets** → força tudo a ser código; código é o que a IA faz melhor;
  elimina a classe inteira de problemas "baixar/licenciar/carregar arquivo".
- **Condição de fracasso na arte** → a IA não "decide" o visual, só executa.
  O autor sabia renderização e transferiu o conhecimento pro prompt.
- **Estrela declarada** → orçamento de atenção desproporcional no que importa.
- **Harness primeiro** → ataca a maior fraqueza de IA em trabalho visual:
  ela não vê o que produz; sem harness, ela ASSUME que ficou bom.
- **Crítico separado do executor** → quem fez o código tem viés pra aprovar.
- **Milestones jogáveis** → nunca existe estado "tudo quebrado, confia".

## 3. Mapa completo de categorias de um jogo (4 camadas)

Checklist para o jogo novo: para CADA categoria, decidir explicitamente
**entra / corta / é a estrela**. Nada fica de fora por esquecimento.

### Camada 1 — Núcleo
| Categoria | O que é | No Wave-Racer |
|-----------|---------|---------------|
| Gameplay / mecânicas | O que o jogador FAZ; o feel do controle | Física do barco (drift, boost, airtime) |
| Level design | O espaço onde se joga | Circuito: retas, hairpin, chicane, saltos |
| Balanceamento / dificuldade | Curva entre frustrante e entediante | Rubber-banding moderado; IAs que erram |
| **Game feel / juice** | Resposta tátil de cada ação | "Weighty, satisfying"; screenshake; FOV kick |

> **Regra do game feel**: toda ação do jogador responde em 3 canais ao mesmo
> tempo — visual, sonoro e movimento/câmera. Por isso HUD+câmera+áudio eram
> UM agente só no prompt: juntos eles SÃO o game feel. É a categoria que mais
> separa "demo de IA" de "jogo publicado".

### Camada 2 — Apresentação
| Categoria | O que é | No Wave-Racer |
|-----------|---------|---------------|
| Gráficos / direção de arte | Estilo e técnica de renderização | Cel-shaded NPR (Guilty Gear Xrd + Wave Race 64) |
| VFX / partículas | Espuma, spray, trilhas, brilhos | Dentro do sistema de água |
| Personagens / animação | Quem habita o jogo, como se move | Riders animados em código ("no T-posed statues") |
| Som / música | Feedback sonoro e atmosfera | Síntese Web Audio (motor, água, impactos) |
| Atmosfera / worldbuilding | O mundo parecer um lugar | Sky dome, nuvens gráficas, paleta fixa |
| UI / HUD + feedback | Informação chegando ao jogador | Velocímetro, minimapa, splits, contramão |

### Camada 3 — Estrutura
| Categoria | O que é | No Wave-Racer |
|-----------|---------|---------------|
| Narrativa / história | Enredo, diálogo, por que você está ali | **Cortada de propósito** |
| Progressão / replayability | O que faz voltar | Só "play again immediately" (mínimo) |
| Onboarding / tutorial | Como se aprende a jogar | Resolvido por design: gênero conhecido + countdown |
| Save / persistência | Progresso, recordes, config | Ausente |
| Multiplayer / social | Jogar com/contra pessoas | Fora de escopo (multiplica complexidade ~5×) |

### Camada 4 — Fundação
| Categoria | O que é | No Wave-Racer |
|-----------|---------|---------------|
| Controles / input | Teclado/gamepad/touch, deadzone, buffer | **Gap do prompt original** — ficou implícito |
| Performance | 60fps no hardware-alvo | Agente dedicado; "stutters = failed game" |
| Acessibilidade | Daltonismo, remapeamento, texto | Ausente |

**Lição do Wave-Racer**: cobriu quase toda a camada 1 e 2 com qualidade alta,
cortou a 3 quase inteira, tratou performance como primeira classe. A lista de
categorias não é fixa — muda por gênero (num RPG a estrela seria narrativa;
num jogo de terror, som e atmosfera).

## 4. O motor de qualidade — triângulo de verificação

```
  ┌─────────────┐   captura    ┌─────────────┐
  │  EXECUTOR   │ ──────────►  │    OLHO     │  harness determinístico
  │ (subagente) │              │  MECÂNICO   │  (screenshots, WAVs, métricas)
  └─────▲───────┘              └──────┬──────┘
        │                             │ evidência real
        │ defeitos nomeados           ▼
        │                      ┌─────────────┐
        └───────────────────── │    JUIZ     │  crítico severo, separado,
                               │   SEVERO    │  régua "jogo publicado"
                               └─────────────┘
```

1. **Olho mecânico ANTES de qualquer feature** — Playwright headless,
   screenshots determinísticos, mesmos ângulos, mesmos momentos. Para áudio:
   gravação + checks numéricos. Toda alegação é comparada com evidência real.
2. **Juiz severo, separado do executor** — só olha evidência, nomeia defeitos
   ESPECÍFICOS ("espuma parece estática"), proibido de aprovar por educação.
3. **Loop até secar** — corrigir → capturar → julgar. Parada: "o juiz não
   nomeia mais nenhum defeito específico". NÃO é nota (nota oscila — medimos
   ±2,5 pontos no juiz Gemini em runs idênticos; defeito nomeável é estável).

Engrenagens de suporte:
- **Milestones jogáveis** (o Wave-Racer usou 8) — cada etapa roda de verdade.
- **Honestidade forçada** — "se está em 70%, diga 70% e por quê".
- **Régua final humana** — o dono ouve/joga; juiz de IA acha defeito, humano
  decide gosto (aprendido nas rodadas de áudio r2→r6).

## 5. Template do prompt-fábrica (slots a preencher)

```
[1 AMBIÇÃO]     Jogo de <GÊNERO> em <TECNOLOGIA>, qualidade de produto
                publicado. Não é demo, não é protótipo.
[2 RESTRIÇÕES]  Stack fechada (Vite+TS+<lib>). npm install && npm run dev.
                ZERO assets externos — tudo procedural/sintetizado.
                <HARDWARE-ALVO> a 60fps; instancing/LOD/DPR adaptativo.
[3 ARTE]        Estilo: <1 ESTILO>. Referências: <2-3 JOGOS REAIS>.
                Técnicas: <NOMEADAS>. FRACASSO se: <CONDIÇÃO EXPLÍCITA>.
[4 ESTRELA]     <O SUBSISTEMA QUE CARREGA O JOGO> — trate como problema AAA
                próprio; agente dedicado; mais iterações que tudo.
[5 MECÂNICAS]   <NÚMEROS E COMPORTAMENTOS VERIFICÁVEIS A OLHO/OUVIDO>
                + decisão entra/corta/estrela pra cada categoria das 4 camadas
                (não esquecer: game feel 3 canais, controles explícitos,
                onboarding, replay mínimo).
[6 MÉTODO]      Subagentes por subsistema contra arquitetura definida antes.
                Harness de captura ANTES de qualquer feature.
                Crítico severo separado; loop até secar defeitos nomeáveis.
                <N> milestones, cada um jogável. Honestidade de %.
[7 ENTREGA]     Repo, README, código comentado, comandos funcionais.
                Ultracode.
```

Diferenças deliberadas vs. o original (upgrades nossos):
- **Controles explícitos** no bloco 5 (gap do original).
- **Checklist de categorias** pra decisão consciente de corte.
- **Expectativa realista**: mesmo com o prompt perfeito, planejar 1-2 rodadas
  de crítica pós-output (o Wave-Racer bruto tinha gaps — lockout morto,
  meia-exigência de HUD faltando). O prompt é o começo, o loop é o resto.

## 6. Sugestões de jogos que encaixam na fórmula

Critérios de encaixe: browser + zero assets viável; UMA estrela visual/sonora
clara; mecânicas verificáveis por screenshot/gravação; sem narrativa pesada;
escopo de corrida única / sessão curta.

### A) **Ink Tide** — corrida/pintura em tinta viva ⭐ candidato natural
- **Conceito**: você pilota um pincel-veículo sobre papel infinito; a tinta
  se espalha, escorre e vira o próprio rastro/pista. Oponentes disputam
  território pintado (estilo Splatoon 2D/3D estilizado).
- **Estrela**: simulação/render de tinta (fluido estilizado, sangramento no
  papel, arrasto do pincel) — problema AAA próprio, 100% shader.
- **Por quê**: já é o nome do projeto; herda TUDO do Wave-Racer (fluido
  estilizado ≈ água; NPR é a linguagem natural de tinta; território pintado é
  verificável por screenshot com precisão de pixel — o juiz vira quase
  determinístico).
- **Game feel**: peso do pincel carregado de tinta, derrapada que borra,
  respingo no impacto.

### B) Corrida de snowboard/downhill cel-shaded
- **Estrela**: neve deformável (trilhas persistentes, spray de pó).
- **Por quê**: transposição 1-pra-1 do molde (neve no lugar de água); risco:
  parecido demais com o que já fizemos — aprende menos.

### C) Wingsuit/planador entre cânions
- **Estrela**: vento visível (linhas de fluxo, nuvens volumétricas gráficas)
  + sensação de velocidade.
- **Por quê**: game feel extremo (proximidade do chão = risco/recompensa);
  câmera e FOV são o coração — tudo verificável por captura.

### D) Rhythm-runner sintetizado
- **Estrela**: o SOM — a fase é gerada pela música sintetizada (Web Audio),
  obstáculos no beat.
- **Por quê**: usa nossa infra de áudio (harness + juiz Gemini) como
  verificador PRINCIPAL, não secundário. É o único que inverte a fórmula:
  estrela sonora, não visual. Risco: juiz de áudio tem variância ±2,5.

### E) Combate naval arcade em arena (1v3)
- **Estrela**: a água de novo, mas com impactos/explosões estilizadas.
- **Por quê**: reaproveita o oceano Gerstner que já dominamos; muda o gênero
  (corrida → arena). Meio termo entre segurança e novidade.

### Recomendação
**A (Ink Tide)** — melhor razão novidade/aproveitamento: mantém a fórmula
(fluido estilizado + NPR + corrida), mas o problema-estrela é NOVO (tinta ≠
água), o nome do projeto já aponta pra ele, e a verificação por screenshot
fica MAIS forte que no original (território pintado é mensurável em pixels —
o crítico ganha um componente objetivo). Segunda opção: **D**, se quisermos
apostar tudo na infra de áudio que construímos.
